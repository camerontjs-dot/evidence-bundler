# DECISIONS.md - Local Evidence Bundler

This file records architecturally significant decisions made throughout the build. Each entry follows ADR (Architecture Decision Record) format. Decision substance is append-only: add a superseding entry if a decision changes. Wording may be cleaned up when packaging the public repository, as long as the decision and rejected alternatives remain intact.

**Trigger conditions for a new entry** - log a decision here when it involves:
- Data model or schema shape (object names, field types, nullable vs. required)
- Retrieval strategy or algorithm selection
- Technology or library choice (with evaluated alternatives)
- Pipeline stage boundaries or handoff contracts
- A constraint that rules out a whole class of future options
- A reversal or amendment of a prior decision

Do not log file placement, naming conventions, or workflow preferences. Those do not need an ADR.

Open and unresolved decisions stay out of this public decision log until they become accepted ADRs.

Naming note: active project docs now use **Local Evidence Bundler**. Historical ADR wording may still use **Evidence Builder** where it records the original contract role name.

## ADR-012 - Accept C-A/C-B v1.1.0 vocabulary passthrough (`format_only` workflow condition)

**Status:** Accepted - 2026-05-17

**Context:**
The apparatus vocabulary moved from v1.0.0 to v1.1.0 by adding `format_only` as a fourth value to `workflow_condition`. The MINOR bump preserves the existing `baseline`, `provenance_scaffold`, and `full_scaffold` values. Evidence Bundler is a downstream consumer: it does not generate `workflow_condition`, but it reads it through C-A intake and writes it through to C-B. Accepting both v1.0.0 and v1.1.0 prevents compatible scaffold runs from failing intake solely because the controlled vocabulary gained one allowed value.

The contract change is explicitly "vocabulary passthrough only - no schema or behavioral changes" per the portfolio decision. The Bundler's job is to accept v1.1.0 inputs and not corrupt them, not to act differently on `format_only`.

**Options considered:**
- A. **Strict-bump passthrough.** Replace `CONTRACT_VERSION = "1.0.0"` with `"1.1.0"` and replace `ContractVersion: Literal["1.0.0"]` with `Literal["1.1.0"]`. Existing fixtures and bundles at v1.0.0 stop validating because the Pydantic field and the file-level `CONTRACT_VERSION` string-equality check in `contracts/intake.py` both reject `"1.0.0"`. Loses backward compatibility for v1.0.0 inputs - incompatible with the portfolio decision's "Existing artifacts remain valid" requirement.
- B. **Dual-version acceptance (chosen).** `CONTRACT_VERSION = "1.1.0"` (the version the Bundler emits going forward), plus a new `SUPPORTED_CONTRACT_VERSIONS: frozenset[str] = frozenset({"1.0.0", "1.1.0"})` for the set of versions Bundler accepts at intake. `ContractVersion: Literal["1.0.0", "1.1.0"]` lets Pydantic validate both. `WorkflowCondition: Literal` adds `format_only`. The intake check at `contracts/intake.py:182` switches from strict equality (`version != CONTRACT_VERSION`) to membership (`version not in SUPPORTED_CONTRACT_VERSIONS`). Writer-side self-check at `contracts/writer.py:330` stays strict - the writer always emits exactly `CONTRACT_VERSION` and verifies its own output. Existing v1.0.0 fixtures stay byte-identical and continue to validate; new fixtures generated by the bumped writer carry `1.1.0`.
- C. **Stay at v1.0.0 in Bundler, bump only on canonical and harness.** Leaves the Bundler embedded vocab and pin out of sync with canonical - `audit_workspace.py` keeps reporting drift, and the harness's v1.1.0 scaffold runs cannot pass through the Bundler's intake even though the only new thing is the vocabulary value. Defers the work without removing it. Rejected because the portfolio decision explicitly bound consumer updates to the same change-control event.

**Decision:** Option B.

**Consequences:**
- `schema/vocabulary.yaml` is now byte-identical to the canonical v1.1.0 copy (SHA-256 `30e2ac74144185c8009d8224ecb67dd628b0b74244647c9051104334d05526bb`). `schema/.contract-version` reads `1.1.0`.
- `src/evidence_bundler/models/common.py`: `CONTRACT_VERSION` bumped to `"1.1.0"`; new `SUPPORTED_CONTRACT_VERSIONS = frozenset({"1.0.0", "1.1.0"})` added; `ContractVersion` Literal widened to accept both versions; `WorkflowCondition` Literal extended with `format_only`.
- `src/evidence_bundler/contracts/intake.py`: the version-mismatch check accepts any version in `SUPPORTED_CONTRACT_VERSIONS`. The error-message substring `"CONTRACT_VERSION is"` is preserved so the existing deviation-classifier path (`_classify_integrity_errors`  to  `vocabulary_drift`) keeps catching truly out-of-band versions like `0.9.0`.
- `tests/test_hashing.py::test_embedded_vocabulary_is_byte_identical`: the hardcoded pin literal was bumped from `"1.0.0"` to `"1.1.0"` to track the explicit pin bump above. This is the only test-assertion change in this ADR. The other 191 test assertions are unchanged; the byte-identical canonical check (the test's primary purpose) still runs unaltered. v1.0.0 fixtures under `tests/fixtures/` stay byte-identical and continue to validate through the widened intake.
- No behavioral change to retrieval, review, finalize, or coverage paths. The C-B writer continues to emit `schema_version="1.1.0"` going forward (the same value as `CONTRACT_VERSION`), which CAL accepts under its parallel widening (CAL DECISIONS.md § 2026-05-17). The synthetic Phase 4 handoff demo and the FDA Phase 5 demo both continue to round-trip end-to-end against the bumped CAL.
- Audit-trail discipline: this ADR captures the rule, the reason, and the alternative considered so a future debugger can recover why both the constant and the supported-set exist. The supported-set exists because the Bundler's writer commits to a single emit version while its reader must accept the closed set of vocabulary-passthrough-compatible versions; collapsing them back to a single constant would re-introduce strict-equality breakage on the next MINOR bump.

**Pre-merge verification (2026-05-17, this branch):**
- `.venv/bin/ruff check .`  to  all checks pass.
- `.venv/bin/python -m pytest`  to  192 passed, 1 skipped, 3 FAISS/SWIG deprecation warnings. The earlier local baseline was 188 passing tests; the four-test delta is the three handoff-demo tests plus the byte-identical pin tracking test, all of which now pass under v1.1.0.
- `.venv/bin/python -m compileall src`  to  no errors.

**Cross-component coordination:**
- Apparatus contract decision from 2026-05-15: the v1.1.0 MINOR bump.
- Canonical contract vocabulary: `schema/vocabulary.yaml` in this repository mirrors `contract_version: "1.1.0"`.
- Downstream audit adapter accepted the same vocabulary widening on 2026-05-17.

**Rejected alternatives:** A (strict-bump passthrough) loses v1.0.0 backward compatibility. C (defer Bundler bump) leaves drift in place against the portfolio decision.

## ADR-011 - Four-state ReviewDecision enum with separate annotation artifact

**Status:** Accepted - 2026-05-12

**Context:**
Phase 3 (Review, Refinement & Output) is the next deliverable after Phase 2b's lexical-vs-hybrid comparison artifact. ADR-001 frames retrieval as nomination, not verification: a `CandidateEvidence` is a candidate until a reviewer records a decision. Earlier design notes named `ReviewDecision` as a canonical object that the review step writes, but the implementation still needed to commit to the states themselves, where the state lives in the artifact tree, how it interacts with `evidence_role` (made required by ADR-010), and how `finalize-bundle` interprets each state when assembling the reviewed C-B bundle.

What is pre-decided going into ADR-011:
- The state list must include at minimum a keep, a drop, and a defer state. Earlier design notes named four states explicitly: `accepted`, `rejected`, `needs-review`, and `insufficient-excerpt`.
- C-A v1.0.0 and C-B v1.0.0 contracts cannot change in this phase. `reviewer_sign_off` already exists on `BundleManifest` in C-B v1.0.0 with a `required: bool` field - Phase 0's fixture writer ships `required=false`; ADR-011 must specify when `required=true`.
- `evidence_role` on `CandidateEvidence` is already required (ADR-010); ADR-010's Consequences already note that `review_status` is orthogonal to `evidence_role`.
- The user locked two workflow constraints on 2026-05-12 ahead of this ADR. **Draft  to  Annotate  to  Finalize:** `build-bundle` keeps producing a draft retrieval C-B; the new `review` CLI (Unit 2) writes a separate annotation YAML against that draft; the new `finalize-bundle` CLI (Unit 4) reads draft + annotations + refines + emits the final reviewed bundle. **Refiner stays narrow:** ADR-010's contradiction-vs-supporting dedup remains in `contracts/writer.py`; the Phase 3 refiner only collapses near-identical excerpts.
- Audit-trail and traceability are non-negotiable across the bundler - the artifact set must let a future reader (or a future debugger) recover the final bundle, the draft retrieval state, the review decisions, and the drift detection anchors that bind them. This applies as much to optimization and troubleshooting as it does to the portfolio claim's provenance stance.

What this ADR has to commit to: the four states and their semantics, where review state is stored, whether and how the reviewer can override the retriever's `evidence_role` (or whether the two are strictly orthogonal), and how `finalize-bundle` (lands in Unit 4) interprets each state when assembling the reviewed C-B bundle and when flipping `reviewer_sign_off.required`. The ADR commits to *structure*; the CLI surfaces (Unit 2 annotator, Unit 4 finalize-bundle) and the refiner (Unit 3) land in their own units against this committed structure.

**Options considered:**
- A. Four-state, separate annotation file, orthogonal, hybrid finalize. States: `accepted` / `rejected` / `needs-review` / `insufficient-excerpt`. Review state lives in a `review_annotations.yaml` artifact written outside the sealed C-B bundle dir, carrying `draft_bundle_id`, `draft_bundle_hash` (recomputed via `compute_bundle_tree_hash`), and `retrieval_config_hash` (copied from the draft bundle manifest's `evidence_builder.config_hash`) so drift on either anchor raises a typed error at load. `ReviewDecision` is orthogonal to `evidence_role` - the reviewer cannot retag a candidate from `supporting` to `contradicting` through review; that gap is handled by reject + re-retrieve. `finalize-bundle` ships `accepted` candidates as-is with their retriever-assigned `evidence_role` routing; ships `needs-review` candidates exactly as `accepted` AND flips `BundleManifest.reviewer_sign_off.required=true` AND records the count distinctly in the coverage report; drops `rejected` candidates and records under `rejected`; drops `insufficient-excerpt` candidates and records under a distinct `insufficient-excerpt` row (not collapsed with `rejected`) so a follow-up retrieval pass has the signal to widen the excerpt span.
- B. Three-state, separate annotation file, orthogonal, hybrid finalize. States: `accepted` / `rejected` / `needs-review`. `insufficient-excerpt` is collapsed into `rejected` with reviewer notes used to convey the reason. Smallest enum and least cognitive load, but loses the structured signal that the *passage* is relevant while the *excerpt span* is wrong - exactly the case the bundler could act on in a future re-retrieval primitive but a generic reject cannot, because notes are free-form text and cannot drive a deterministic retry. Also departs from the committed four-state design without an amendment.
- C. Four-state, on `CandidateEvidence` directly, orthogonal, hybrid finalize. States and finalize semantics as A, but review state lives as a new `review_status: ReviewDecision = "needs-review"` field on `CandidateEvidence`; the draft bundle's claim files carry review state inline. One artifact and no drift detection - but directly violates the user-locked Draft  to  Annotate  to  Finalize workflow because it couples retrieval state to review state, forces draft bundles to be mutable, makes review non-re-runnable without rebuilding retrieval, and would require either adding `review_status` to C-B v1.0.0 (contract violation) or hiding it in a sidecar that defeats the "one artifact" upside.
- D. Four-state, separate annotation file, reviewer may override `evidence_role`, hybrid finalize. As A, but `ReviewAnnotation` includes an optional `override_evidence_role: EvidenceRole | None = None` that lets the reviewer retag a candidate (e.g., supporting  to  contradicting) at review time; final C-B routing uses the override when present. Closes the real gap where ADR-010's text-pattern gate miscategorizes a passage and the only correction path today is reject-and-rerun, but breaks ADR-010's clean orthogonality - `evidence_role` would no longer be "what the retriever called it" but "what the retriever called it, possibly overridden by the reviewer" - and complicates dedup, reporting, and provenance because the bundle now carries two role attributions (retriever and reviewer). Reasonable as a future ADR if the gap becomes a measured pain point; pulls scope into ADR-011 today.
- E. Five-state with `accepted-with-edit`, separate annotation file, orthogonal, hybrid finalize. As A plus an `accepted-with-edit` state where the reviewer indicates the excerpt should be modified before shipping (e.g., narrowed or rewrapped). More expressive - captures "right passage, wrong span" as a positive (keep) rather than negative (drop) signal - but implies the bundler can mutate excerpts. The C-B `passage_text` is the evidentiary span; edits belong in CAL's audit step, not Bundler. The bundler's job is curation, not text editing. `insufficient-excerpt` + reject + re-retrieve already covers the "wrong span" case.
- F. Four-state, new field in C-B v1.1.0. States as A; add `review_status` to C-B `ClaimEvidencePassage` and `counterevidence_passages` entries; bump the contract to v1.1.0. Single artifact and review state visible to CAL - but the contract version bump cascades to CAL and ships review semantics into a contract layer that should describe evidence shape, not review provenance. Explicitly out of scope per the user's Draft  to  Annotate  to  Finalize choice; the implementation scope also treated "no C-A/C-B v1.0.0 changes" as a non-negotiable.
- G. Four-state, separate annotation file, orthogonal, strict finalize (only `accepted` ships). States and storage as A; `finalize-bundle` ships only `accepted` candidates; `needs-review` is treated identically to `rejected` and excluded from C-B; `reviewer_sign_off.required=true` whenever any candidate was not explicitly `accepted`. Makes review a hard gate matching the strict reading of ADR-001's "review step is what makes evidence valid". High friction for large corpora - every candidate must be touched before any bundle ships; defeats the value of `needs-review` as a deferred-decision state because deferring becomes equivalent to rejecting; reviewer fatigue likely pushes everything to bulk-accept, weakening the meaning of `accepted`.
- H. Four-state, separate annotation file, orthogonal, permissive finalize (only `rejected` drops). As A but `insufficient-excerpt` also ships into C-B (alongside `accepted` and `needs-review`); only `rejected` excludes a candidate. Minimal reviewer commitment - but `insufficient-excerpt` by definition means the matched span is too narrow to evaluate, so shipping it conflates "reviewable evidence" with "retrieval artifact that needs another pass". Reviewer notes attached to `insufficient-excerpt` candidates would land in CAL without the bundler having acted on them, weakening the structured signal `insufficient-excerpt` is supposed to carry.

**Decision:** Option A.

The four-state list matches the committed implementation design and preserves `insufficient-excerpt` as a structured signal the bundler can act on. The separate annotation artifact respects the user-locked Draft  to  Annotate  to  Finalize workflow and keeps the draft bundle immutable, which is essential for re-runnable review and for the audit-trail / traceability stance: retrieval state and review state are preserved independently and bound only by hashes, so each can be debugged, re-run, or compared without disturbing the other. Orthogonality with `evidence_role` preserves the clean ADR-001 / ADR-010 stance (retriever nominates a role; reviewer records a decision; the two are different attributions). Hybrid finalize semantics make `needs-review` a genuine deferred state rather than a synonym for `rejected`, while `reviewer_sign_off.required=true` surfaces partial-review state to CAL without blocking the bundle on real-corpus scale.

**Consequences:**

- A new `ReviewDecision = Literal["accepted", "rejected", "needs-review", "insufficient-excerpt"]` is added to the models package. The four members are the only valid values; new states require a superseding ADR.
- A new `ReviewAnnotation` Pydantic model captures one review row per draft-bundle candidate. Fields: `claim_id: NonBlankStr`, `passage_id: NonBlankStr` (the `auto-{source_id}-{digest12}` id minted by `contracts/writer.py:_retrieved_passage_id`), `source_id: NonBlankStr`, `evidence_role: EvidenceRole` (snapshot from retrieval; imported from `models.retrieval`), `decision: ReviewDecision = "needs-review"`, `reviewer_notes: str | None = None`, `decided_at_utc: NonBlankStr | None = None`. Models use the project's existing `StrictBaseModel` with `extra="forbid"`.
- A new `ReviewAnnotationFile` Pydantic model wraps the annotation list with audit-trail anchors. Fields: `schema_version: NonBlankStr` pinned to `CONTRACT_VERSION`, `draft_bundle_id: NonBlankStr`, `draft_bundle_hash: HashValue` (recomputed via `compute_bundle_tree_hash`), `retrieval_config_hash: HashValue` (copied from the draft bundle manifest's `evidence_builder.config_hash`), `generated_at_utc: NonBlankStr`, `reviewer: NonBlankStr | None = None`, `annotations: list[ReviewAnnotation]`. The two hash fields are the drift-detection anchors that bind a set of review decisions to the exact draft retrieval state they were taken against; any tracked-file mutation in the draft bundle or any retrieval-config change after annotation invalidates the file at load time.
- A new typed exception `ReviewAnnotationDriftError` lives alongside the loader. It is raised when `file.draft_bundle_hash` does not match `compute_bundle_tree_hash(draft_bundle_dir)`, when `file.draft_bundle_id` does not match the draft manifest's `bundle_id`, or when `file.retrieval_config_hash` does not match the draft manifest's `evidence_builder.config_hash`. The error message names which anchor mismatched so a future debugger can recover the cause without re-running the diff manually.
- `ReviewDecision` is orthogonal to `evidence_role`. The 4×4 product (`{supporting, contradicting, conditional, insufficient} × {accepted, rejected, needs-review, insufficient-excerpt}`) is fully valid at the Pydantic level. No constraint couples the two. ADR-010 already establishes that the `insufficient` retrieval role never reaches a reviewable candidate (it is report-only and never lands in C-B), so the practical product is 3×4 - but the Pydantic schema does not enforce that, on purpose, because narrowing the schema to the practical product would couple the review model to ADR-010's gate-output rules and break the orthogonality stance.
- The draft retrieval bundle (produced by `build-bundle`) remains immutable across the entire review and finalize lifecycle. `review_annotations.yaml` is written outside the sealed C-B bundle dir (analogous to retrieval reports), so `compute_bundle_tree_hash` over the draft bundle stays meaningful as a stability anchor and `build-bundle` re-runs against the same C-A produce byte-identical drafts (modulo timestamps).
- `finalize-bundle` (lands in Unit 4) interprets each `ReviewDecision` as follows:
  - `accepted` - candidate ships into final C-B with its retriever-assigned `evidence_role` routing (supporting  to  `evidence_passages`; contradicting/conditional  to  `counterevidence_passages`, per ADR-010).
  - `rejected` - candidate is excluded from final C-B. The coverage report records the count under `rejected`.
  - `needs-review` - candidate ships into final C-B exactly as `accepted` would, **and** `BundleManifest.reviewer_sign_off.required` flips to `true`, **and** the coverage report records the count under a distinct `needs-review` row so the partial-review state is legible to CAL.
  - `insufficient-excerpt` - candidate is excluded from final C-B. The coverage report records the count under a distinct `insufficient-excerpt` row (not collapsed with `rejected`) so a follow-up retrieval pass has the signal to widen the excerpt span. Reviewer notes attached to `insufficient-excerpt` decisions remain in the annotation file for later retrieval-side action.
- `evidence-bundler review` (CLI sub-group, Unit 2 deliverable) and `evidence-bundler finalize-bundle` (Unit 4 deliverable) are out of scope for ADR-011 itself - the ADR commits to *structure*; the units commit the UX.
- C-A v1.0.0 and C-B v1.0.0 contracts are unchanged. `reviewer_sign_off` is already a v1.0.0 field on `BundleManifest`; `required=true` is already a valid state - Phase 0's fixture writer ships `required=false`, and `finalize-bundle` is the writer that flips it.
- Audit-trail layout for Phase 3: the draft retrieval bundle, the `review_annotations.yaml`, the refiner's transformation log (Unit 3 surface), the final reviewed bundle, and the coverage report are all separable artifacts. Any of them can be reconstructed or re-run from the upstream pieces given the same retrieval config and the same review decisions. This is the audit-trail-by-design property the project's portfolio claim rests on and the property a future debugger relies on when something needs to be optimized or fixed without re-litigating settled state.

- **Pre-merge testing commitments.** ADR-011 is purely structural - no model choice or pattern is being deferred to corpus data, so there is no comparison-report A/B for this ADR. The five tests below must be green deterministically before the Unit 1 implementation merges. Each maps to a specific deterministic test that could be written today against the committed `scaffold-run-mixed-formats` fixture and the existing `build_retrieval_bundle` library call.

  1. **State enumeration round-trip.** Parametrize over the four `ReviewDecision` values. Each value serializes to YAML via `model_dump(mode="json")` and reloads identically through Pydantic. Fast deterministic test.
  2. **Scaffold correctness.** Build a hybrid draft bundle from the committed `tests/fixtures/scaffold-run-mixed-formats/` fixture (use the existing `build_retrieval_bundle` library call, not the CLI). Call `scaffold_annotations_from_bundle()`. Assert: (a) one `ReviewAnnotation` per `evidence_passages` + `counterevidence_passages` entry across all claim files; (b) every annotation has `decision="needs-review"` and `decided_at_utc is None`; (c) every `evidence_role` matches the container the passage came from (supporting from `evidence_passages`; contradicting as the recorded default from `counterevidence_passages` - Unit 5 may revisit if the contradicting/conditional distinction becomes load-bearing in coverage reporting); (d) annotation list is sorted by `(claim_id, source_id, passage_id)`. Fast deterministic test.
  3. **Drift detection - bundle hash.** Scaffold annotations from a fresh draft bundle, write them, then mutate any tracked file inside the draft bundle (touch one byte). Assert `load_review_annotations` raises `ReviewAnnotationDriftError` with a message identifying the bundle-hash mismatch. Fast deterministic test.
  4. **Drift detection - config hash.** Scaffold annotations, edit the YAML file's `retrieval_config_hash` to a different value, assert the loader raises `ReviewAnnotationDriftError` identifying the config-hash mismatch. Fast deterministic test.
  5. **Orthogonality.** Parametrize over the 4×4 product of `EvidenceRole × ReviewDecision` (4 roles × 4 decisions = 16 combinations). Construct a `ReviewAnnotation` for each combination; assert each instantiates without raising. Fast deterministic test.

  Schema preservation is verified by the existing suite - `build-bundle` and `build-fixture-bundle` smoke runs must still pass byte-for-byte (modulo timestamps), and the existing 113 tests must remain green. Not a new test, but a green-boundary requirement for the Unit 1 merge.

- **Revision triggers.**
  - If a future Phase 5 real-corpus demo shows reviewer-vs-retriever role disagreement is a measurable pain point (i.e., reviewers frequently reject candidates with notes that say "wrong role, not actually contradicting"), Option D (reviewer override of `evidence_role`) is revisited as a superseding ADR. The amendment records the measurement (count, fraction of rejects with role-disagreement notes) and the alternative considered - even if the conclusion is "the gap is not large enough to justify the orthogonality break."
  - If a future Phase 4 CAL handoff demo shows that `needs-review` shipping into final C-B with `reviewer_sign_off.required=true` confuses the audit step (e.g., CAL treats `needs-review` candidates identically to `accepted` and the partial-review state is invisible downstream), the finalize semantics shift toward Option G (strict - only `accepted` ships) in a superseding ADR.
  - If reviewer fatigue (Phase 5 real-corpus) shows `bulk-accept` is the dominant primitive and `accepted` is being applied without genuine per-candidate review, Unit 2's batch primitives gain a `--require-explicit-accept` gate (UX-layer mitigation, not ADR-011 amendment), and the coverage report adds a `bulk_accepted` distinction to keep the audit trail honest about how `accepted` was reached.
  - Any ADR-011 amendment from the above triggers records null and negative findings with the same discipline as positive ones, per the ADR-009 / ADR-010 pattern: the measurement, the alternative considered, the decision, and the rationale all land in the amendment so a future reader can recover the reasoning even if the default does not change.

- **Phase 5 real-corpus measurement record - 2026-05-13.** Phase 5 measured reviewer-vs-retriever role disagreement and batch-accept prevalence on the pinned FDA CGMP guidance demo via `scripts/run_phase_5_fda_guidance_demo.py`; generated artifacts live under `build/phase-5-fda-guidance-demo/adr011_review_measurements.*`. The deterministic review sequence produced 46 annotation rows, 17 reviewer-vs-retriever role-disagreement rows (`0.370`), 15 accepted rows, and a `1.000` batch-accept fraction among accepted rows. Result: no ADR-011 schema or finalize-semantics amendment is promoted from this run. Option D (reviewer override of `evidence_role`) remains available, but this run's disagreement rows are primarily rejected retrieval spillover rather than accepted final-bundle rows requiring a second role attribution. No `--require-explicit-accept` UX mitigation is promoted because the run intentionally used deterministic batch review; it establishes a baseline count, not a real reviewer-fatigue measurement.

- Option B (three-state) was rejected because collapsing `insufficient-excerpt` into `rejected` discards a structured signal the bundler can act on in a future re-retrieval primitive - reviewer notes are free-form text and cannot drive a deterministic retry - and because the committed four-state design would require an amendment before departure.
- Option C (state on `CandidateEvidence`) was rejected because it couples retrieval state to review state, forces the draft bundle to be mutable, makes review non-re-runnable without rebuilding retrieval, and either violates the C-B v1.0.0 contract or hides review state in a sidecar that defeats the "one artifact" upside. Directly conflicts with the user-locked Draft  to  Annotate  to  Finalize workflow.
- Option D (reviewer override of `evidence_role`) was rejected because it breaks ADR-010's clean orthogonality stance - the bundle would carry two role attributions (retriever and reviewer), complicating dedup, reporting, and provenance - and because the gap it closes is not yet a measured pain point. Available as a future ADR if Phase 5 real-corpus evidence justifies the orthogonality break.
- Option E (five-state with `accepted-with-edit`) was rejected because the bundler does not edit excerpts; the C-B `passage_text` is the evidentiary span, and any edits belong in CAL's audit step. `insufficient-excerpt` + reject + re-retrieve already covers the "wrong span" case.
- Option F (C-B v1.1.0 contract bump) was rejected because the contract version bump cascades to CAL, ships review semantics into a contract layer that should describe evidence shape, and violates the user-locked "no C-A/C-B v1.0.0 changes" non-negotiable.
- Option G (strict finalize - only `accepted` ships) was rejected because it makes review a hard gate that collapses `needs-review` into `rejected` in practice, defeats the value of `needs-review` as a deferred-decision state, and on real-corpus scale produces reviewer fatigue that pushes everything to bulk-accept. Available as a future ADR if Phase 4 CAL handoff evidence shows partial-review state confuses the audit step.
- Option H (permissive finalize - only `rejected` drops) was rejected because shipping `insufficient-excerpt` into final C-B conflates "reviewable evidence" with "retrieval artifact that needs another pass" and weakens the structured signal `insufficient-excerpt` is meant to carry. Reviewer notes attached to `insufficient-excerpt` decisions would land in CAL without the bundler having acted on them.

**Source:** ADR-001 nomination framing; ADR-010 `evidence_role` consequences; implementation design notes from 2026-05-12.

## ADR-010 - Contradiction retrieval as a first-class pass with text-gated role tagging

**Status:** Accepted - 2026-05-12

**Context:**
Phase 2b Unit 5 adds a contradiction-and-conditional retrieval pass on top of the Phase 2a BM25 baseline (ADR-006), the ADR-008 hybrid RRF stack, and the ADR-009 parent-level reranker. The research proposal's `counterevidence_recall` metric requires the bundler to *produce* disconfirming candidates, not merely accept them when a human flags them - so the contradiction pass is part of the apparatus, not a Phase 3 review concern. ADR-001 frames retrieval as nomination, not verification: the bundler nominates an evidence role, the reviewer confirms it.

What is pre-decided going into ADR-010:
- Contradiction retrieval is a separate pass over the same indexes, not a re-tagging of supporting-pass results.
- `evidence_role: Literal["supporting", "contradicting", "conditional", "insufficient"]` already exists on `CandidateEvidence` from the v2.1 schema work.
- C-B `counterevidence_passages` already exists in v1.0.0 - no contract change required (ADR-002).
- The pass reuses the Phase 2a max-score parent aggregation rule (ADR-006) and the Phase 2b hybrid stack (ADR-008).
- `contradiction_enabled` and `contradiction_top_k` knobs already exist on `RetrievalConfig` from Unit 1.
- The reranker default and structural placement are locked by ADR-009; this ADR must decide whether and how the reranker runs on the contradiction pass.

What this ADR has to commit to: contradiction query construction, role-tagging rules and the text-pattern gate that backs them, the dedup policy when a passage appears in both passes, reranker interaction with the contradiction pass, the treatment of the `insufficient` role, and v1 config defaults. The ADR commits to *structure*, not to optimal patterns or models - calibration belongs to the comparison-report deliverable.

**Options considered:**
- A. Fixed-prefix query reformulation + text-pattern role gate + same hybrid stack as supporting + separate `contradiction_rerank_enabled` knob (default `False`) + contradiction-wins-on-dedup + `insufficient` report-only + opt-in via `contradiction_enabled: bool = False`. Deterministic prefixes default to `["evidence against", "limitations of", "contradicts the claim that", "does not support", "fails to demonstrate"]` (per `coding-references/rag-pipeline.md` § Contradiction Retrieval Pass) and live as `contradiction_query_prefixes: list[str]` on `RetrievalConfig`, so domain prefixes (pharma/regulatory) can be added via config and participate in the config hash. Text gate: disconfirming patterns  to  `contradicting`; limiting/exception patterns  to  `conditional`; neither  to  `insufficient`. `evidence_role` becomes required (no default) on `CandidateEvidence`, forcing all construction sites to set it explicitly. `contradicting`/`conditional` route to `counterevidence_passages`; `supporting` routes to `evidence_passages`; `insufficient` appears in the retrieval run report only and never in C-B. Reviewer overrides any role via `review_status` (orthogonal to `evidence_role`).
- B. Re-tag from the supporting pass. No second retrieval. Scan supporting candidates for disconfirming language and re-tag them. Misses the vocabulary-mismatched disconfirming passages that the prefix-reformulated queries are designed to surface - those passages don't appear in the supporting pool because the original claim query doesn't match them. Conflicts with the pre-decided "first-class pass" framing and undercuts the apparatus's `counterevidence_recall` metric by anchoring counterevidence to supporting-query recall.
- C. LLM-generated query reformulations. Most expressive query construction; could capture domain idioms the prefix list misses. Breaks determinism, adds an LLM dependency to a stack that has stayed local through OQ-3 (semantic) and OQ-7 (rerank), and would require a `llm_assisted=True` provenance line on every nominated counter-candidate. Out of step with v1's local-only stance.
- D. Pass-derived role tagging (no text gate). Every contradiction-pass hit is tagged `contradicting`; the limiting/conditional shape is collapsed away. Simpler. But prefix-query spillover can surface clean *supporting* passages (the prefix is short relative to the claim text and the dominant attention is on the claim itself), and tagging those `contradicting` over-claims a role the bundler has not verified. Conflicts with ADR-001's nomination-not-verification framing.
- E. Reranker inherits the supporting-pass setting. No separate contradiction-rerank knob; if `rerank_enabled` is on, the cross-encoder reranks both passes. Cheaper config surface. The cross-encoder default `cross-encoder/ms-marco-MiniLM-L-6-v2` is trained on MS MARCO passage-relevance pairs and scores topical relevance - a passage that says "Drug X showed no significant effect" is topically identical to "Drug X is effective" and may score equally high. The reranker can therefore silently downrank disconfirming passages below topically-similar supporting passages, defeating the purpose of the pass. There is no comparison-report data yet to falsify or confirm this concern. A separate default-off sibling knob preserves the test matrix without violating ADR-009's structure.
- F. Default-on for hybrid (`contradiction_enabled: bool = True` when `retrieval_method == "hybrid"`). Symmetric with the research proposal's requirement that `counterevidence_recall` be measurable on the apparatus output. Breaks parity with ADR-009's opt-in stance (`rerank_enabled: bool = False`) and makes dep-tier reasoning ambiguous. Opt-in is cleaner and matches the project's pattern of "feature is available; default behavior is the baseline that has comparison data."
- G. `insufficient` as a new C-B field. Surface insufficient candidates in the bundle so reviewers can see the gate's near-misses. Requires a C-B v1.0.0 contract change, which violates ADR-002 and would need a formal contract/version decision. Out of scope for ADR-010.
- H. Supporting-wins-on-dedup. When the same parent passage appears in both passes after the contradiction text gate, the supporting tag is preserved and the contradiction-pass match is dropped. Reads as conservative - the bundler never "downgrades" support to counterevidence. The text gate has already filtered spurious matches, so a dedup hit means the passage genuinely contains disconfirming or limiting language; preserving the supporting tag understates counterevidence visibility, not the other way around. Reviewer can always override.

**Decision:** Option A.

**Consequences:**
- `src/evidence_bundler/retrieval/contradiction.py` owns three components: `build_contradiction_queries(claim_text, prefixes) -> list[str]`, the contradiction retrieval pass (BM25 + semantic + RRF + ADR-006 aggregation; optionally reranks per `contradiction_rerank_enabled`), and `classify_role(passage_text) -> EvidenceRole` (the text-pattern gate). `evidence_bundler/contracts/writer.py` consumes the resulting `CandidateEvidence` list and routes by role.
- `RetrievalConfig` additions/changes:
  - `contradiction_query_prefixes: list[str]` - defaults to the five prefixes from `coding-references/rag-pipeline.md`. Participates in the config hash, so any domain-prefix extension is reproducibly recorded on the run report.
  - `contradiction_rerank_enabled: bool = False`. Validator: may only be `True` when `rerank_enabled` and `contradiction_enabled` are both `True`. Reuses the same reranker model loaded for the supporting pass - no second model weights, no new dep tier.
  - `contradiction_text_gate_enabled: bool = True` - explicit switch so the comparison report can A/B gate-on vs gate-off. Default `True` matches the conservative-tagging stance.
  - `contradiction_enabled: bool = False` (already in config; this ADR confirms the v1 default).
- `CandidateEvidence.evidence_role` becomes required (no default). All construction sites in BM25, semantic, and hybrid retrieval code must set `evidence_role="supporting"` explicitly; the contradiction pass sets `"contradicting"`, `"conditional"`, or `"insufficient"` per the text gate.
- Text-pattern gate (initial v1 pattern set; refined by Test 3 below):
  - Disconfirming to `contradicting`: word-boundary, case-insensitive matches against `no`, `not`, `did not`, `does not`, `failed`, `failure`, `never`, `however`, `contrary to`, `contradicts`, `refutes`, `disproves`, `no significant effect`, `no effect`, `ineffective`, `not effective`.
  - Limiting  to  `conditional`: `only when`, `only if`, `except`, `limited to`, `restricted to`, `provided that`, `subject to`, `contraindicated`, `not applicable to`, `not indicated`, `in patients [over/under/with]`, `for [population]`.
  - Priority: if both pattern groups match, `contradicting` wins (disconfirmation is the stronger epistemic shape).
  - Neither matches  to  `insufficient`.
- Dedup policy: when the same parent passage appears in both passes after aggregation, the contradiction-pass tag wins and the candidate routes to `counterevidence_passages`. The supporting-pass nomination for that passage is dropped from `evidence_passages`. Reviewer can override via `review_status`.
- C-B routing: `supporting`  to  `evidence_passages`; `contradicting` and `conditional`  to  `counterevidence_passages`; `insufficient`  to  not in bundle. C-B v1.0.0 contract preserved.
- Report additions: per-claim `contradicting_hits`, `conditional_hits`, and `insufficient_hits` counts; a `no_countercandidate_claim_ids` list when `contradiction_enabled`; capped top contradicting/conditional/insufficient excerpts for diagnostic visibility. Reports must continue to use nomination language ("counter-candidate nominated", "no counter-candidate found") - counter-candidates are nominations, not verified counterevidence.
- A claim with neither supporting nor counterevidence candidates remains a valid no-candidate output in C-B; reports distinguish "no supporting candidate" from "no counter-candidate" so the two failure modes are not conflated.
- Dep tiers stay clean: BM25 (rank-bm25 only)  to  hybrid (+ sentence-transformers, faiss-cpu)  to  hybrid+rerank (+ cross-encoder weights)  to  hybrid+contradiction (no new deps beyond the text-gate regex module)  to  hybrid+rerank+contradiction-rerank (no new deps beyond what rerank already pulls).

- **Pre-merge testing commitments.** ADR-010 is the structural commitment; the v1 defaults (prefix list, gate patterns, default-off rerank-on-contradiction) need calibration data before they harden. The Phase 2b comparison-report deliverable runs the following experiments and records findings in an ADR-010 amendment or superseding ADR **regardless of whether they show improvement** - same discipline as ADR-009. Null and negative results are recorded with the same rigor as positive ones, to preserve the audit trail and prevent silent drift back to default assumptions.

  1. **Rerank 2×2 matrix.** Same C-A fixture, same claims, four runs: (rerank-off-supporting, rerank-off-contradiction); (rerank-on-supporting, rerank-off-contradiction - the recommended v1 default); (rerank-off-supporting, rerank-on-contradiction); (rerank-on-supporting, rerank-on-contradiction). Measure `counterevidence_recall` against the contradicting/conditional fixture expectations; measure delta in supporting precision/recall as a control. Hypothesis to falsify: a relevance reranker silently suppresses disconfirming passages.
  2. **Prefix-set comparison.** Default five prefixes vs default plus a small domain-pharma set (candidates: `"contraindicated in"`, `"failed primary endpoint for"`, `"off-label use of"`, `"adverse events from"`). Measure delta in `counterevidence_recall` and the false-positive rate (passages tagged `contradicting`/`conditional` that the fixture marks as supporting).
  3. **Text-gate calibration.** Run with `contradiction_text_gate_enabled: false` vs the default `true`. If gate-on and gate-off produce identical `counterevidence_passages` lists, the gate is doing no work and the patterns must be tightened. If gate-on drops contradicting hits that gate-off captures, the pattern lists need expansion. Either outcome lands in an ADR-010 amendment to the pattern set.
  4. **Dedup stress test.** Construct a fixture passage that contains both supporting and disconfirming language for the same claim (e.g., a passage that says "Drug X is effective for hypertension; however, no effect was seen in patients over 65"). Verify the dedup-wins-on-contradiction rule routes the passage to `counterevidence_passages` as `contradicting` when both pattern groups match, not to `evidence_passages` as `supporting`. Deterministic fast test.
  5. **No-countercandidate visibility.** Verify that a claim with zero contradiction hits remains valid C-B output, surfaces in the report's `no_countercandidate_claim_ids` list, and does not collapse into a "no-candidate" claim (which is a different state). Deterministic fast test.

  Implementation should not merge until Tests 4 and 5 are green deterministically (fast fixture-only tests) and Tests 1–3 have a recorded result in the Phase 2b comparison-report artifact - even if the recorded result is "no significant delta detected on this corpus, revisit on the real-corpus demo (Phase 5)."

- **Revision triggers.**
  - If Test 1 shows rerank-on-contradiction *improves* `counterevidence_recall` without harming supporting precision, the default flips to `True` in a superseding ADR.
  - If Test 2 shows domain prefixes materially improve `counterevidence_recall`, the default `contradiction_query_prefixes` list is amended (still a list, still config-hash-bound, still a structural ADR-010 amendment because the recorded list is part of the audit trail).
  - If Test 3 shows the gate is suppressing real disconfirming hits, the disconfirming/limiting pattern lists are expanded. The default state of the gate (`True`) is not changed by this test - only the patterns inside it.
  - Phase 5's real-corpus demo will re-run all five tests on a non-synthetic corpus; any divergence from fixture-corpus findings is recorded as an ADR-010 amendment.
  - Option E may be revisited as a v2 simplification if Test 1 shows rerank-on-contradiction is neutral; the comparison-report data justifies the simpler config surface.

- **Implementation comparison record - 2026-05-12.** Phase 2b Unit 5 recorded ADR-010 Tests 1-3 in `reports/report_20260512_173211.md`. The rerank-off / contradiction-rerank-on matrix cell is intentionally not runnable because the ADR-010 validator requires `rerank_enabled=True` before `contradiction_rerank_enabled=True`; the remaining runnable cells showed no fixture-basis for flipping the default. Default plus pharma-domain prefixes did not improve counter-candidate recall or reduce false-positive counter passages on the fixture. Disabling the text gate increased false-positive counter passages, so no pattern loosening is justified. Result: no superseding ADR and no default-prefix or pattern amendment from this fixture record.

- **Phase 5 real-corpus measurement record - 2026-05-13.** Phase 5 re-ran the ADR-010 matrix, prefix-set comparison, and text-gate calibration on the pinned FDA CGMP guidance corpus via `scripts/run_phase_5_fda_guidance_demo.py`; generated artifacts live under `build/phase-5-fda-guidance-demo/adr010_measurements.*`. The rerank-off / contradiction-rerank-on matrix cell remains intentionally non-runnable because `contradiction_rerank_enabled` requires `rerank_enabled=True`. Expected counter-claim recall was `3/3` across runnable matrix and prefix/gate runs, but false-positive counter-candidate counts were high (`20` with the default text gate). The pharma-domain prefix expansion did not improve the coarse expected-claim recall measure and increased false positives to `21`; disabling the text gate increased false positives to `25`. Result: no default, prefix-list, or gate-pattern amendment is promoted from this real-corpus run. The finding is documented publicly as counter-candidate spillover risk rather than hidden as a retrieval success.

- Option B (re-tag from supporting) was rejected because the pre-decided "first-class pass" framing exists specifically to surface vocabulary-mismatched disconfirming passages that the supporting query cannot reach.
- Option C (LLM reformulations) was rejected for v1: breaks determinism and adds an LLM dep tier that the local stack has avoided through OQ-3 and OQ-7.
- Option D (no text gate) was rejected because pass-derived tagging over-claims `contradicting` on prefix-spillover matches and conflicts with ADR-001's nomination-not-verification framing.
- Option E (no separate rerank knob) was rejected because a relevance reranker plausibly suppresses disconfirming passages and no comparison-report data exists yet to falsify the concern; a default-off sibling knob preserves the test matrix without violating ADR-009 structure.
- Option F (default-on for hybrid) was rejected to keep parity with ADR-009's opt-in stance and to keep dep-tier reasoning clean.
- Option G (`insufficient` as a C-B field) was rejected because it would require a C-B v1.0.0 contract change, violating ADR-002.
- Option H (supporting-wins-on-dedup) was rejected because the text gate already filters spurious contradiction matches, so a dedup overlap is a genuine signal that the passage qualifies the claim; preserving the supporting tag would understate counterevidence visibility.

## ADR-009 - Parent-level cross-encoder reranking with single configurable model

**Status:** Accepted - 2026-05-11

**Context:**
Phase 2b Unit 4 adds a third retrieval stage on top of the Phase 2a BM25 baseline and ADR-008 hybrid RRF. ADR-003 already commits to parent-level reranking in principle ("Phase 2b applies cross-encoder reranking at the parent level after hybrid retrieval and child-to-parent aggregation"). ADR-006 fixes max-score parent aggregation; ADR-008 fixes equal-weight RRF over BM25 and semantic child rankings; ADR-001 frames retrieval as nomination, not verification.

What remains is the rerank algorithm's structure: where it sits in the pipeline, what it sees as input, what its score replaces or augments, what model it loads by default, and how its results stay legible alongside the prior lexical/semantic/fusion signals. The default cross-encoder was already named in implementation design notes (`cross-encoder/ms-marco-MiniLM-L-6-v2`), and the `rerank_enabled`/`rerank_model`/`rerank_top_n` config fields already exist from the first config slice. What this ADR has to commit to is the structure, not the optimal model - there is no validation data on this corpus yet.

**Options considered:**
- A. Parent-level rerank after RRF + ADR-006 aggregation. Single configurable cross-encoder, default `cross-encoder/ms-marco-MiniLM-L-6-v2`, loaded behind a `load_reranker_model` boundary that mirrors `load_embedding_model`. Cross-encoder input is `claim + parent_text` only. Rerank score replaces final parent ordering; `lexical_score`, `semantic_score`, `fusion_score`, and a new internal `rerank_score` all stay visible on `CandidateEvidence` and in retrieval reports. Opt-in via `rerank_enabled: bool = False`. Deterministic tie-breaking: `rerank_score` desc  to  `fusion_score` desc  to  parent `char_start`  to  `chunk_id`. Larger rerankers (e.g., `BAAI/bge-reranker-base`) are a documented upgrade path, swap-in via config.
- B. Child-level rerank before parent aggregation. Cross-encoder sees the matched span, which would be a stronger per-chunk signal. Contradicts ADR-006 because parent selection would no longer be a max-score-over-children rule - rerank-driven child selection would need its own aggregation contract. Also requires reranking 50–100 fused children per claim vs ~30 parents.
- C. Rerank replaces fusion entirely. One ranking signal, no RRF tuning. Loses the cross-retriever agreement signal RRF was introduced for; the rerank model becomes a single point of epistemic failure. Cannot recover "this chunk only matched lexically" or "both retrievers agreed" tells once the cross-encoder reorders by its own attention.
- D. Blended score (`α × fusion + (1 − α) × rerank`, or product). Keeps both signals in the ordering. Reintroduces the weighting/normalization problem ADR-008 explicitly rejected for weighted RRF - cross-encoder logits and RRF sums are on incompatible scales, α has no principled default, and the choice would drift from its last-justified value without re-evaluation.
- E. Ensemble rerankers (RRF over two cross-encoder rerank lists). Restores agreement-signal logic at the rerank stage and matches the project's "no single point of epistemic failure" stance. Costs 2× latency and 2× weights for marginal expected benefit when the rerankers are similar, and reintroduces the weighting/selection question. Worth revisiting after the Phase 2b comparison report yields data; not a v1 commitment.
- F. Augmented cross-encoder input (`claim + parent_text + matched_child_excerpt`). Tells the cross-encoder which child triggered retrieval. Wastes tokens against the model's 512-token cap (the child is already inside the parent) and biases an independent judge by imposing the lexical/semantic retrievers' attention pattern on a model whose value comes from its own attention pattern.

**Decision:** Option A.

**Consequences:**
- `src/evidence_bundler/retrieval/reranker.py` will own cross-encoder calls and expose a `ParentReranker` (or equivalent) with a `rerank(claim, parents)` method that returns parents in rerank-score order, plus a `load_reranker_model` factory mirroring `load_embedding_model`. The model boundary is config-driven; swapping to a larger reranker is a config change, not a code change.
- Default model is `cross-encoder/ms-marco-MiniLM-L-6-v2` (~22M params). `BAAI/bge-reranker-base` (~280M params) is documented as the upgrade path; both are to be validated against the Phase 2b comparison report deliverable. The ADR does not claim the default is optimal - only that it is the minimum honest v1 for a pipeline that has no calibration data yet.
- Rerank input is `claim + parent_text` only. `CandidateEvidence.matched_child_chunk` is preserved for reviewer trace and report excerpts but is not fed into the cross-encoder.
- Rerank score replaces final parent ordering. `lexical_score`, `semantic_score`, `fusion_score`, and a new internal `rerank_score: float | None` all remain visible on `CandidateEvidence` and are surfaced in retrieval reports. No new fields land in C-B; ADR-002's v1.0.0 contract is preserved.
- Opt-in via `rerank_enabled: bool = False` (the existing config default). `--method hybrid` continues to write valid C-B bundles without the cross-encoder dependency materialized; opting into rerank adds a one-time cross-encoder weight download. Dep tiers stay clean: BM25 (rank-bm25 only)  to  hybrid (+ sentence-transformers, faiss-cpu)  to  hybrid+rerank (+ cross-encoder weights).
- Rerank is bounded by `rerank_top_n` (current default 30). The reranker sees at most that many parents per claim; final output is still capped by `top_k`.
- Deterministic tie-breaking when two parents share a rerank score: higher `fusion_score`, then parent `char_start`, then `chunk_id` lex order. Cross-encoder float ordering can drift across hardware/library versions; the fallback chain prevents non-determinism.
- Option B (child-level rerank) was rejected because it contradicts ADR-006's max-score parent aggregation rule and would require a new aggregation contract, expanding the unit's scope beyond a single ADR.
- Option C (rerank replaces fusion) was rejected because it discards the cross-retriever agreement signal that ADR-008 was introduced to capture, collapsing nomination back to a single judge.
- Option D (blended / normalized score fusion) was rejected for the same reason ADR-008 rejected weighted normalized-score fusion: cross-scale normalization has no principled default and reintroduces drift risk for a knob that has no validation data.
- Option E (ensemble rerankers) was rejected for v1 because the cost-benefit case requires comparison-report data the project does not yet have; revisiting it is a future-ADR move, not a v1 requirement.
- Option F (augmented input) was rejected because the matched-child excerpt is already inside the parent text and wastes the cross-encoder's token budget while biasing its independent judgment.
- **Revision trigger:** the Phase 2b comparison-report deliverable will A/B (a) hybrid vs hybrid+rerank, (b) `cross-encoder/ms-marco-MiniLM-L-6-v2` vs `BAAI/bge-reranker-base`, and (c) single reranker vs RRF-over-two-rerankers. The findings will be recorded in an ADR-009 amendment or superseding ADR **regardless of whether they show improvement** - null and negative results are recorded with the same discipline as positive ones, to preserve the audit trail and prevent silent drift back to default assumptions.

**Source:** RAG pipeline reference notes and ADR-009 implementation scope notes from 2026-05-11.

## ADR-008 - Equal-weight Reciprocal Rank Fusion at the child level

**Status:** Accepted - 2026-05-11

**Context:**
Phase 2b Unit 3 needs to combine BM25 and semantic child/leaf rankings into a single ordered list that feeds the existing `parent_aggregator`. ADR-003 fixes the parent-child hierarchy and the index-child / return-parent pattern. ADR-006 fixes max-score parent aggregation for the lexical baseline. ADR-007 fixes the FAISS semantic index. The implementation design specifies RRF and child-level fusion. What remains is the actual fusion algorithm, its determinism properties, and the default config knobs (candidate pool, k constant).

Per-method score visibility is required for reports (lexical, semantic, fusion). Aggregation up to parents must continue to use the ADR-006 max-score rule, now applied over fusion scores. C-A/C-B v1.0.0 must not change; the fusion score is internal to `CandidateEvidence` and never reaches C-B.

**Options considered:**
- A. Equal-weight Reciprocal Rank Fusion (Cormack et al. 2009) at the child level: `score(d) = Σ_i 1 / (k + rank_i(d))` summed across each retriever's ranked child list, default k=60, default 50 candidates per retriever. Score-normalization-free; trivially extensible to a third ranking (contradiction pass) by appending a list. Tie-breaks resolved deterministically by best lexical rank, then best semantic rank, then `chunk_id` lex order.
- B. Weighted RRF: same shape but with per-list weights configurable. Adds a tuning surface with no data to tune against in v1; weights risk drifting from their last-justified values without re-evaluation.
- C. Weighted normalized-score fusion (convex combination of normalized BM25 and cosine): `score(d) = α * norm(bm25) + (1 - α) * norm(semantic)`. Requires score normalization (min-max or z-score), which `coding-references/rag-pipeline.md` explicitly rejects because the scales are incompatible and normalization introduces arbitrary distortion. α has no principled default.
- D. Parent-level fusion: run BM25 and semantic child rankings through `parent_aggregator` independently, then RRF over the parent-level rankings. Contradicts the Phase 2b plan's child-level fusion stance and loses the cross-retriever child-level signal (a parent surfaced by both retrievers via the *same* child gets no boost).

**Decision:** Option A.

**Consequences:**
- `src/evidence_bundler/retrieval/hybrid.py` implements RRF as a pure function over a list of ranked child-id lists. `reciprocal_rank_fusion(rankings, k=60)` returns `(chunk_id, fusion_score)` pairs ordered descending by fusion score.
- Default config values (already present from Unit 1): `rrf_k_constant = 60`, `rrf_candidate_pool = 50`. Both configurable via `RetrievalConfig`; defaults match Cormack et al. 2009 and the worked example in `coding-references/rag-pipeline.md` § Reciprocal Rank Fusion.
- Tie-breaking order when two chunks share a fusion score: best lexical rank, then best semantic rank, then `chunk_id` lexicographic. Fully deterministic - does not depend on Python dict ordering or list-insertion order.
- Internal child-hit objects carry `lexical_score`, `semantic_score`, `fusion_score`, and stable `rank`. None of these new fields land in C-B; ADR-002's v1.0.0 contract is preserved.
- Parent aggregation continues to use the ADR-006 max-score rule, with fusion score as the input. `parent_aggregator` itself does not change; only the child score it consumes changes when `--method hybrid` is selected.
- Retrieval reports for `--method hybrid` show: RRF k constant, candidate pool per retriever, child-hit counts (lexical-only / semantic-only / overlap), top lexical/semantic/fusion scores per claim, unique parent counts, and no-candidate claims. Per-method score visibility is preserved so the Phase 2b lexical-vs-hybrid comparison artifact can reason about retriever-level deltas.
- Adding a third or fourth ranked list (contradiction pass in Unit 5, optional multi-query expansion later) is a one-line change at the call site - no fusion-algorithm change required.
- Option B was rejected because v1 has no corpus-level evidence to justify non-uniform weights, and the extra knob risks drifting from its last-justified value without re-evaluation. Weighted RRF remains a clean future extension that does not break Option A's API.
- Option C was rejected because cross-scale score normalization is the exact failure mode `coding-references/rag-pipeline.md` calls out; min-max is outlier-sensitive and z-score assumes Gaussian, neither of which holds for BM25 vs. cosine.
- Option D was rejected because it loses the cross-retriever child-level agreement signal and would require amending the Phase 2b plan's child-level fusion stance.

**Source:** RAG pipeline reference notes for reciprocal rank fusion.

## ADR-007 - FAISS IndexFlatIP semantic index with directory-artifact persistence

**Status:** Accepted - 2026-05-11

**Context:**
Phase 2b adds semantic child/leaf retrieval on top of the Phase 2a BM25 baseline. OQ-3 already resolved the embedding model to `BAAI/bge-small-en-v1.5`, config-driven via `RetrievalConfig`. ADR-003 fixes that retrieval indexes child/leaf chunks and returns parent context through `parent_aggregator`. ADR-006 fixes the Phase 2a max-score aggregation rule. What remains is the local store/index boundary: how embeddings are computed, indexed, persisted between runs, and rebuilt when the C-A corpus changes. The Phase 2b plan explicitly defers this choice to a deliberate ADR before any semantic dependency is added.

Expected corpus scale is 5K–50K chunks (Phase 5 real-corpus demo with PubMed Central / FDA guidance subsets). Exactness, dependency footprint, determinism in fixture tests, and the ability to reuse the Phase 2a child-rank-list interface for RRF fusion are higher-value than metadata-query capability inside the store.

**Options considered:**
- A. FAISS `IndexFlatIP` exposed as a `semantic_index/` directory artifact (`vectors.faiss`, `chunks.jsonl`, `manifest.yaml`). Exact nearest-neighbour at this scale, deterministic, ~30 lines of glue per `coding-references/rag-pipeline.md`. Manifest carries `corpus_hash`, embedding model, dimension, and chunk count; mismatched manifest on load forces rebuild. Two files inside the directory but a single artifact at the API and SHA256SUMS layer.
- B. ChromaDB embedded `PersistentClient`. One store for embeddings, ids, and metadata, but pulls in DuckDB, Apache Arrow, sqlite-backed metadata, and a client/server layer even in embedded mode. API has churned across recent minor versions. The metadata-filter capability is unused because parent aggregation runs after retrieval, not inside the store.
- C. SQLite FTS5 + `sqlite-vec` extension. Lightest dep footprint (sqlite is stdlib, extension is a small loadable lib); one file holds everything. Newer than the other two with fewer worked examples for "top-k ranked indices for RRF" specifically, and requires `enable_load_extension` plus manual BLOB packing/unpacking for embeddings. More custom glue, less battle-tested for the deterministic top-k pattern Phase 2b needs.

**Decision:** Option A.

**Consequences:**
- `faiss-cpu` is a runtime dependency. Windows, macOS (Intel + Apple Silicon), and Linux (x86-64 + ARM64) all have official wheels on PyPI from 1.13.x onward, so cross-platform install is `pip install faiss-cpu` with no source build.
- `src/evidence_bundler/retrieval/embedding_retriever.py` owns FAISS calls and exposes a `SemanticIndex` with `build(chunks, model, …)`, `save(path)`, `load(path)`, and `ranked_indices(query, top_k)`. Callers see one path; the multi-file layout is internal.
- Persistence layout is a directory `semantic_index/` containing `vectors.faiss`, `chunks.jsonl` (row index to `chunk_id` map plus `parent_chunk_id` for downstream aggregation), and `manifest.yaml` (`corpus_hash`, `embedding_model`, `embedding_dim`, `chunk_count`, `built_at`). `load(path)` validates the manifest against the current C-A `corpus_hash` and the configured embedding model; a mismatch triggers rebuild rather than silent reuse.
- The indexed set is the same child/leaf chunk set BM25 indexes - child chunks with `parent_chunk_id` plus flat fallback chunks with no children. Parent context still comes from the existing `parent_aggregator`; this ADR does not change ADR-003 or ADR-006.
- The default embedding model is `BAAI/bge-small-en-v1.5` (OQ-3), config-driven via `RetrievalConfig.embedding_model`. The BGE retrieval query prefix is applied to queries only, never to corpus chunk texts. `normalize_embeddings=True` is required so that inner product equals cosine similarity under `IndexFlatIP`.
- `IndexFlatIP` is exact at the 5K–50K chunk scale; ANN indexes (HNSW, IVF) are not adopted in Phase 2b and would require a separate ADR if the corpus grows past the documented ~500K threshold.
- Option B was rejected because the heavy dep footprint and unused metadata-filter capability work against the project's dep-light stance and add API-churn risk for no functional gain in this access pattern.
- Option C was rejected because the marginal dep saving does not offset the custom glue and lower familiarity for the deterministic top-k / RRF pattern Phase 2b needs. It remains a documented future option if FAISS ever becomes untenable on a target platform.

**Source:** RAG pipeline reference notes for semantic retrieval and reciprocal rank fusion.

## ADR-006 - BM25 lexical baseline with max-score parent aggregation

**Status:** Accepted - 2026-05-11

**Context:**
Phase 2a needs the first end-to-end retrieval path from C-A corpus to C-B bundle without taking on semantic retrieval, hybrid fusion, reranking, or contradiction search. Phase 1 already emits deterministic parent-child chunks. ADR-003 fixes that retrieval should index child/leaf chunks and return parent context, but left the aggregation rule open.

**Options considered:**
- A. BM25Okapi over child/leaf chunks with max-score parent aggregation - deterministic, dependency-light, interpretable, and enough to establish the lexical baseline for later hybrid comparison.
- B. Mean-score parent aggregation - rewards multiple weak child hits, but can bury one strong passage inside a long parent section.
- C. Start with hybrid retrieval immediately - better recall target, but collapses Phase 2a and Phase 2b and removes the clean lexical-only comparison artifact.

**Decision:** Option A.

**Consequences:**
- `rank-bm25` is a runtime dependency and `BM25Retriever` indexes only leaf chunks: child chunks with `parent_chunk_id`, plus flat fallback chunks that have no children.
- `parent_aggregator` maps `child.parent_chunk_id or child.chunk_id` to parent context and uses the maximum child lexical score as the parent score. Ties resolve by best child rank, parent `char_start`, then parent chunk id.
- C-B stores the aggregated parent passage with `extraction_method: auto_retrieved`; the retrieval report records child-hit counts, unique-parent counts, top scores, no-candidate claims, and the matched-child excerpt.
- `semantic_score` remains `None`, `retrieval_method` is `"bm25"`, `llm_assisted` is `False`, and `evidence_role` defaults to `"supporting"` until Phase 2b adds semantic/hybrid/rerank and contradiction retrieval.
- A no-candidate claim is a valid outcome. The claim still appears in C-B with an empty passage list, and the report names it explicitly.

## ADR-005 - PDF extraction behind a unified extractor interface

**Status:** Accepted - 2026-05-11

**Context:**
Phase 1 Unit 3 adds PDF ingestion to the same `SourceDocument` and `DocumentChunk` flow used by Markdown and plain text. The PDF library selection was already resolved by OQ-4: `pdfminer.six` is primary because layout-aware extraction matters for regulatory/pharma PDFs, and `pypdf` is fallback because simple generated or clean-text PDFs can still be read when pdfminer returns no text. The implementation still needs a boundary that prevents loader code and tests from depending directly on either library.

**Options considered:**
- A. Call `pdfminer.six` directly from `loader.py` - minimal code, but makes fallback and failure classification harder to test without loader-specific branching.
- B. Use `pypdf` only - simpler install and faster extraction, but worse fit for complex regulatory PDFs and contrary to OQ-4.
- C. Add a `PDFExtractor` interface with `backend="auto" | "pdfminer" | "pypdf"`, pdfminer primary, pypdf fallback, and typed failure classification.

**Consequences:**
- `src/evidence_bundler/ingest/pdf_extractor.py` owns PDF library calls. `loader.py` dispatches `.pdf` content through that interface and receives extracted text only.
- `PDFExtractionError` classifies current Unit 3 failures as `empty_text` or `extractor_error`. Scanned/image-only PDFs are therefore explicit empty-text failures; OCR remains deferred.
- `SourceDocument.content_hash` remains the hash of the original `content.pdf` bytes, not the extracted text. This preserves C-A original-record integrity while allowing `raw_text` to feed the internal chunker.
- PDF table detection is not introduced here. PDF text is chunked through the existing plain-text path; Markdown pipe-table preservation remains the only table-aware behavior in Phase 1.

## ADR-004 - Recursive splitter with heading-path, section-tag, and table-aware handling

**Status:** Accepted - 2026-05-10

**Context:**
ADR-003 fixes the chunk hierarchy (parent-child) but not the splitter that produces it. Phase 1 chunking has to handle three input shapes from C-A `corpus/{source_id}/content.*`: Markdown with headers (regulatory + scientific docs), plain text without structure (extracted PDF tail, scaffold-emitted text), and PDF text once Unit 3 lands. The splitter must be deterministic, dep-light (no LangChain / llama-index splitters), and preserve two structures the bundler downstream relies on: section identity (numbered clauses like `4.2.1`, IMRAD section names) and tables. Tables fragmented mid-row destroy the semantics that pharma QA and regulatory submissions specifically need to cite.

**Options considered:**
- A. Naive fixed-window character split with overlap - simplest, deterministic, but destroys headings, section tags, and table integrity. Forces downstream review to repair what ingest broke.
- B. Markdown header-aware splitter with naive fallback for non-Markdown - preserves Markdown section semantics but produces no section tags, no heading paths, and still fragments tables.
- C. Recursive separator-based splitter (paragraph  to  sentence  to  char) + Markdown header-aware splitter at the parent level + best-effort section-tag extraction + a rule that tables are emitted intact as a single chunk regardless of size. Chunk size and overlap are config-driven via a `ChunkSpec`. No external splitter dependency.

**Decision:** Option C.

**Consequences:**
- `src/evidence_bundler/ingest/chunker.py` implements the splitter pattern documented in `coding-references/chunking-strategies.md`. Header levels map to `chunk_level` (1 to `section`, 2 to `subsection`, 3+ to `paragraph`).
- `DocumentChunk` carries `heading_path: list[str]` (e.g., `["Treatment Guidelines", "First-line therapy"]`) and `section_tag: str | None`. `section_tag` is extracted best-effort from heading text - numeric prefixes (`4.2.1`), IMRAD keywords (`Methods` / `Results` / `Discussion`), or `None` when nothing matches. Never invented.
- Tables (Markdown pipe-table syntax, `^\|.*\|$` lines) are detected as a unit and emitted as a single `DocumentChunk` regardless of `max_chars`. They are never passed through the recursive splitter.
- `ChunkSpec` carries `max_chars` and `overlap_chars`; defaults follow the corpus-type table in `coding-references/chunking-strategies.md` § Overlap and Chunk Size Guidance. Config-driven means a future regulatory corpus can lower `max_chars` for dense clauses without code changes.
- PDF table detection is **explicitly deferred** to Phase 5 if it ever becomes load-bearing. Phase 1 only detects Markdown pipe-tables; PDF tables are treated as flowing text by the recursive splitter.
- No new runtime dependency is added by this ADR. PDF library deps land separately in Unit 3 per OQ-4.
- Option A was rejected because the downstream review and audit steps need section identity and table integrity to be present at retrieval time, not reconstructed.
- Option B was rejected because Phase 5 needs regulatory-numbered sections (FDA guidance, ICH) to surface in the bundle and audit report; a Markdown-only path leaves plain text and PDF without section tags.

**Source:** RAG overview research notes from 2026-05-08.

## ADR-003 - Hierarchical (parent-child) chunking and retrieval

**Status:** Accepted - 2026-05-10

**Context:**
Phase 1 needs a chunking architecture before Unit 2 (chunker implementation). The default RAG pattern is flat chunking: split a document into uniform pieces, index them, retrieve them as-is. For the bundler's primary application domain (pharma QA / regulatory submissions) this destroys the enclosing-section context that defines a clause's meaning. A "should" in a clinical guideline depends on the section that scopes it; a definition reused later in a regulation refers back to the section that introduced it. The bundler's job is to keep that traceable from corpus to audit input.

The research proposal's `counterevidence_recall` metric also depends on retrieving the right unit of evidence - a contradicting paragraph deep inside a "Limitations" section, returned with its parent context, is interpretable; the same paragraph as a bare chunk is not.

**Options considered:**
- A. Flat chunking, retrieve what was indexed. Simplest path, lowest implementation cost. Loses enclosing-section context and produces low-interpretability retrieved excerpts in regulatory-style documents.
- B. Hierarchical parent-child chunking: index child chunks for retrieval precision, return the parent chunk as the evidence context handed downstream. Flat-structure corpora handled as a degenerate case where each chunk's parent is the document itself. Higher schema cost; needs `chunk_level` and `parent_chunk_id` on `DocumentChunk`.
- C. Flat indexing with retrieval-time window expansion (return matched chunk ± N surrounding characters). Cheaper to implement than B but does not respect section boundaries - windows can cross section transitions and bring in irrelevant adjacent text.

**Decision:** Option B.

**Consequences:**
- `DocumentChunk` carries `chunk_level: Literal["document", "section", "subsection", "paragraph", "clause"]` and `parent_chunk_id: str | None`. Document-level chunks have `parent_chunk_id = None`.
- Phase 2a indexes child chunks (typically `paragraph` level) for BM25 retrieval and aggregates hits up to `parent_chunk_id` via a `parent_aggregator`; the bundle output carries parent context alongside the matched-child excerpt.
- Phase 2b applies cross-encoder reranking at the parent level after hybrid retrieval and child-to-parent aggregation. The proposed cross-encoder ADR (still pending) inherits from this hierarchy decision.
- Contradiction retrieval (Phase 2b) operates at the same child level as supporting retrieval; the `evidence_role` field on `CandidateEvidence` is orthogonal to hierarchy.
- Flat-corpus inputs are handled by emitting each top-level chunk with itself as its own parent or with the document as parent. This is a degenerate case of the same code path, not a separate path.
- Option A is rejected because regulatory-document retrieval without enclosing context produces excerpts the audit step cannot reason about.
- Option C is rejected because character-window expansion crosses structural boundaries (sections, definitions, table edges) and so cannot replace structural parent context.
- Open boundary: the actual aggregation rule (max child score? mean child score? top-K children?) is a Phase 2a implementation choice, not part of this ADR. ADR-003 only fixes the hierarchy and the index-child / return-parent pattern.

**Source:** RAG overview research notes from 2026-05-08.

## ADR-010a - Amendment to ADR-010: Contradiction text gate pattern tightening and truncation order

**Status:** Accepted - 2026-06-16

**Context:**
The initial implementation of the contradiction text gate (ADR-010) suffered from two retrieval correctness bugs:
1. **Gate over-match:** The `DISCONFIRMING_PATTERNS` included bare words like `"no"`, `"not"`, and `"however"`. Since these are extremely common in benign supportive or factual passages (e.g., "no adverse events", "however, it was found to be effective"), nearly any retrieved parent passage was tagged as `contradicting` or `conditional`. This resulted in a high false-positive rate (20 false-positives in the FDA guidance demo) and crowded out genuine counterevidence.
2. **Truncation order bug:** The final contradiction candidates were truncated to `contradiction_top_k` *before* filtering out `insufficient` candidates (passages that did not match disconfirming/limiting patterns). As a result, irrelevant `insufficient` matches that ranked higher in semantic/lexical similarity crowded out valid `contradicting` or `conditional` candidates, preventing them from being nominated.

**Options considered:**
- A. **Keep patterns and add proximity gates.** Keep bare `no`, `not`, `however` but restrict matching to within N words of the claim text. This adds complexity and heuristic parameters without resolving the core issue that bare negations are too generic.
- B. **Tighten patterns and correct truncation order (chosen).**
  - Drop the bare patterns `"no"`, `"not"`, and `"however"` from `DISCONFIRMING_PATTERNS`. Keep multi-word patterns (e.g., `"did not"`, `"no significant effect"`, `"no effect"`, `"ineffective"`) and other disconfirming keywords (e.g., `"failed"`, `"failure"`, `"never"`, `"contrary to"`, `"contradicts"`).
  - Modify `retrieve_contradicting` to filter out all `insufficient` candidates *before* performing reranking and the `contradiction_top_k` truncation.

**Decision:** Option B.

**Consequences:**
- Benign passages containing bare "no", "not", or "however" will no longer classify as `contradicting` or `conditional` unless they match specific multi-word negation phrases.
- In the FDA guidance demo, the false-positive counter-candidate count was reduced from 20 to 3 while maintaining a perfect recall of expected counter-claims (3/3).
- `insufficient` candidates are discarded early in the contradiction pass, ensuring that the final bundle's top-k candidates are populated exclusively by actual disconfirming or conditional evidence.
- Standard test suites and demo runners remain fully green.

## ADR-013 - Parent-context synthesis for plain text and PDF files via numeric section headings

**Status:** Accepted - 2026-06-16

**Context:**
For Markdown files, we group paragraphs under their Markdown headings (e.g. `#`, `##`, `###`), creating a parent-child relationship that allows parent-level cross-encoder reranking and preserves local context. However, for plain text (`.txt`) and PDF (`.pdf`) files, the system previously fell back to flat chunking where all chunks are paragraph level and have no parent context (`parent_chunk_id=None`). To improve retrieval correctness and context synthesis, we need to implement parent-context synthesis for flat text and PDF files.

The user clarified that numeric section heading detection (e.g., detecting `1.1`, `2.0`, `4.2.1` headers) is the preferred strategy rather than a simple paragraph-based sliding/chunk window.

**Options considered:**
- A. **Paragraph sliding-window grouping.** Group every 3-5 consecutive paragraphs under a synthetic parent. While simple, this is topic-agnostic and groups unrelated text across section boundaries.
- B. **Numeric section heading detection (chosen).** Parse numeric section headers (e.g., matching a sequence of digits and dots that has at least one dot, such as `1.0`, `1.1`, `4.2.1`, or `1.`, `2.`) and split the text into parent sections and child paragraphs. If no numeric headers are found, fall back to flat chunking.

**Decision:** Option B.
We implement numeric section heading detection. We match lines that start with a numeric prefix containing at least one dot (e.g., matching the regex `^\s*((?:\d+\.)+\d*)(?:\s+|\r?\n)([A-Z][A-Za-z0-9 ,'\-&()]+)$` under multiline mode, which also gracefully handles newlines between the section number and the heading title from PDF extraction).
- If numeric headings are detected, we build a parent chunk for each section and split its body into child paragraph chunks under that parent.
- If a preamble exists before the first section heading, it is chunked as a parent preamble section with child paragraphs.
- If no numeric headings are detected, we fall back to the existing flat paragraph chunking.

**Consequences:**
- Plain text and PDF documents with numeric headings will now produce hierarchical parent-child chunks rather than flat chunks.
- This enables parent-level cross-encoder reranking and preserves surrounding section context for plain text/PDF evidence.
- The chunk set for PDFs in scaffold runs and tests will change. We must update the verification expectations in the test suite and demo scripts.
